# Beauty Assistant — прототип LLM-ассистента по уходовой косметике

Ассистент задаёт пару уточняющих вопросов (тип кожи, проблема, бюджет) и подбирает 3–5 товаров из каталога, объясняя, почему они подходят. Под капотом: семантический поиск в Qdrant с жёсткими фильтрами, LLM-агент на LangGraph с tool calling и eval-набор для измерения качества.

Каталог синтетический: 250 товаров, бренды выдуманы.

## Архитектура

```
пользователь → FastAPI → LangGraph-агент (LLM в Ollama)
                              │ tool calling
                              ├── search_catalog(query, skin_type, max_price, ...)
                              │       └── Qdrant: вектор по описанию + фильтры по payload
                              ├── get_product(id)
                              ├── triage: медицинские признаки → к врачу, до LLM
                              └── verify: проверка ответа кодом перед отправкой
```

## Этапы

| Этап | Что появляется | Статус |
|---|---|---|
| 1. Поиск | каталог, индексация в Qdrant, поиск с фильтрами | готово |
| 2. Агент | LangGraph-агент, tool calling, уточняющие вопросы | готово |
| 3. Оценка | 16 кейсов поиска (P@5, MRR, прирост над случайным), 16 диалогов агента с автопроверками | готово |
| 4. Сервис | FastAPI, автотесты; Qdrant-сервер и Docker Compose | готово |
| 5. Упаковка | README с результатами экспериментов, публикация на GitHub | |

## Запуск (этап 1)

Нужен Python 3.11+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python data/generate_catalog.py   # каталог → data/catalog.json
python -m app.ingest              # индексация (при первом запуске скачается модель ~2,2 ГБ)
python -m app.search "что-то от покраснений, кожа реагирует на всё" --skin чувствительная --max-price 2500 --no-fragrance
```

## Запуск (этап 2)

Нужен [Ollama](https://ollama.com) с моделью, которая умеет tool calling:

```bash
ollama pull qwen2.5:7b
python -m app.agent
```

Другую модель можно подставить через переменную: `OLLAMA_MODEL=llama3.1:8b python -m app.agent`.

## API (этап 4)

```bash
uvicorn app.api:app --reload        # Ollama должна быть запущена
```

Интерактивная документация — http://127.0.0.1:8000/docs.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/chat` | реплика в диалоге; `session_id` из ответа передаётся в следующий запрос, чтобы агент помнил контекст |
| POST | `/search` | поиск по каталогу без LLM, с теми же правилами нормализации фильтров, что у агента |
| GET | `/products/{id}` | карточка товара |
| GET | `/health` | состояние: доступна ли Ollama, сколько товаров в индексе, какие модели |

```bash
curl -X POST localhost:8000/chat -H 'Content-Type: application/json' \
     -d '{"message": "что-нибудь от прыщей, кожа жирная, до 2000"}'
```

В ответе `/chat`, кроме текста, — вызванные инструменты с аргументами, id найденных товаров и число срабатываний `verify`: это делает поведение агента наблюдаемым без чтения логов.

**Решения.** Агент вызывается через `ainvoke`: пока LLM отвечает (5–40 с), сервер обслуживает другие запросы; синхронные поиск и эмбеддинги уходят в пул потоков. Граф и модель эмбеддингов (~2 ГБ) загружаются один раз при старте, а не на первом запросе. Если Ollama выключена — `503` с понятным текстом, а не падение.

### Docker

```bash
docker compose up --build           # Ollama на компьютере должна быть запущена
```

Поднимаются два контейнера: `api` (FastAPI + агент) и `qdrant` (Qdrant в режиме сервера, данные в томе `qdrant_storage`). При первом старте `api` индексирует каталог, при следующих пропускает (`python -m app.ingest --if-empty`). Модель эмбеддингов берётся из папки `models/` на компьютере, поэтому повторно не скачивается и переживает пересборку образа.

**Почему Ollama не в контейнере.** Docker на Mac не даёт контейнеру доступа к GPU Apple (Metal), и LLM работала бы в разы медленнее. Поэтому модель остаётся на компьютере, а контейнер обращается к ней по `host.docker.internal`. В продакшене на её месте был бы отдельный inference-сервер с GPU (vLLM, TGI) по тому же HTTP-протоколу: меняется только `OLLAMA_URL`.

Код один для обоих режимов: если задана переменная `QDRANT_URL`, работа идёт с Qdrant-сервером, если нет, с локальной базой в `qdrant_data/`. Индексы payload (категория, тип кожи, цена, активы), которые локальный режим игнорирует, сервер использует для фильтрации.

### Тесты

```bash
python -m pytest -q
```

7 тестов проверяют механику без Ollama и без скачивания модели: LLM подменяется сценарием ответов, эмбеддинги — детерминированными векторами. Покрыты память диалога, отклонение выдуманного товара `verify`, перехват медицинского случая `triage` до LLM, нормализация фильтров, ошибки 404/422/503. Качество модели проверяют не тесты, а `eval/`.

## Оценка качества (этап 3)

Два слоя, потому что ошибки бывают двух видов: поиск не нашёл нужное или LLM неправильно им воспользовалась.

```bash
python -m eval.run_retrieval_eval --models all     # поиск, без LLM: сравнение моделей эмбеддингов
python -m eval.run_agent_eval                      # агент целиком, нужен Ollama
OLLAMA_MODEL=qwen2.5:14b python -m eval.run_agent_eval
```

**Поиск** (`eval/retrieval_cases.json`). Релевантность задана правилом по структурированным полям каталога («в concerns есть акне»), поэтому эталон точный и не требует ручной разметки. Метрики: precision@5, MRR и **прирост над случайным поиском** — без этой поправки кейсы, где релевантна половина каталога, завышают результат.

**Агент** (`eval/agent_cases.json`). Каждый кейс — диалог из одной или нескольких реплик: ловушки, найденные при ручном тестировании (выдуманные товары на пустой выдаче, потерянный ретинол, смена темы), плюс вне темы и медицинский случай. Проверяются фильтры, с которыми реально прошёл поиск, названные товары и их соответствие условиям. Отдельно меряется, какую долю фильтров LLM передала **сама** — это показывает, сколько держит модель, а сколько страхует код.

Результаты прогонов сохраняются в `eval/results/`.

### Результаты поиска

16 запросов, топ-5 выдачи. «Случайно» — доля релевантных товаров среди прошедших фильтры: столько P@5 дал бы случайный поиск.

| Модель эмбеддингов | P@5 | Случайно | Прирост | MRR | Индексация 250 товаров |
|---|---|---|---|---|---|
| paraphrase-multilingual-MiniLM-L12-v2 | 0.59 | 0.33 | +0.26 | 0.64 | 2.5 с |
| paraphrase-multilingual-mpnet-base-v2 | 0.60 | 0.33 | +0.28 | 0.76 | 3.5 с |
| **multilingual-e5-large** | **0.89** | 0.33 | **+0.56** | **0.94** | 11 с |

- e5-large даёт вдвое больший прирост над случайным поиском и выбрана моделью агента (с префиксами `query:` / `passage:`, на которых она обучена).
- Самый показательный кейс — разговорное слово: на «что-то от прыщей» MiniLM вернула пять пенок без единого средства от акне (P@5 = 0), e5-large — 1.0. Подсказку «прыщи → акне» в описании инструмента пришлось добавить именно из-за слабой модели.
- e5-large провалила один кейс, который у лёгких моделей проходил: «кожа шелушится и стягивает после умывания» → пенки «от покраснений» вместо средств от обезвоживания.
- Цена выбора: модель ~2,2 ГБ против ~0,2 ГБ и в 4 раза медленнее индексация. Для 250 товаров это 11 секунд, для реального каталога понадобится пакетная индексация.

### Результаты агента

Доля пройденных диалогов (Qwen 2.5 через Ollama, MacBook Air M-series, temperature 0):

| Версия | 7B | 14B | Что изменилось |
|---|---|---|---|
| v1 | 53% | 73% | исходный агент, 15 кейсов |
| v2 | 80% | — | тип кожи, тип средства и актив извлекает код; граница темы диалога |
| v3 | **38%** | 94% | правило в промпте «сразу ищи, не спрашивай бюджет» |
| v4 | **88%** | **94%** | откат правила v3; узел `triage`; правки `verify`; 16 кейсов |
| v5 | 88% | — | поиск переведён с MiniLM на multilingual-e5-large |

| Метрика (v4) | 7B | 14B |
|---|---|---|
| Фильтры, переданные самой LLM (без страховки кода) | 79% | 96% |
| Средняя задержка хода | 16 с | 38 с |

**Главные выводы.**
- Основная причина провалов v1 — не галлюцинации (`verify` не сработал ни разу), а потерянные условия: модель не переносила тип кожи и тип средства между репликами. Детерминированное извлечение условий кодом дало больше, чем смена модели.
- **Правка промпта, которая помогла 14B, обрушила 7B с 80% до 38%**: маленькая модель стала писать «Ищем…» вместо вызова инструмента. Без регрессионного прогона это бы не заметили. Правка откачена.
- **Смена модели эмбеддингов не сдвинула долю пройденных диалогов (v4 → v5), хотя P@5 поиска выросла с 0.59 до 0.89.** Это ограничение самой оценки: диалоги проверяют фильтры и поведение, но не смысловую релевантность найденного. Разница видна в ответах — на «прыщи» вместо масок и крема для век агент предлагает средства с салициловой кислотой и цинком. Следующий шаг: проверять, что у названных товаров в `concerns` есть проблема из запроса.
- **`verify` сработал в бою:** в v5 модель 7B посреди ответа перешла на китайский (A11); проверка вернула ответ на переписывание, пользователь получил чистый русский.
- 14B стабильно сильнее, но в 2,4 раза медленнее. Для продакшна выбор зависит от бюджета на задержку; при облачной модели этот компромисс выглядел бы иначе.

**Известные ограничения.**
- 7B: на «SPF для комбинированной кожи» переспрашивает бюджет вместо поиска (A10); предупреждение о беременности держится только на промпте и иногда пропадает (A06) — следующий шаг: добавлять предупреждения по флагам товаров кодом.
- 14B провалила A11 («подробнее про первый»), который проходила в предыдущем прогоне при temperature 0. Один прогон — шумная оценка; для решений между близкими вариантами нужно 3+ прогона на вариант.
- `verify` иногда принимает предложенный бюджет («поднимите до 3000 ₽») за цену несуществующего товара: ответ переписывается, но итог остаётся честным.
- Каталог и проверки синтетические: метрики показывают надёжность механики агента, а не качество косметических рекомендаций.

## Решения и компромиссы

- **Фильтры отдельно от семантики.** Тип кожи, цена и наличие — жёсткие условия: вектор не должен «примерно угадывать» бюджет. Семантика отвечает только за смысл запроса.
- **Вектор по описанию, а не по названию.** В названии мало смысла («Glow сыворотка»), в описании — активы и проблемы кожи.
- **Модель эмбеддингов выбрана по метрикам, а не по умолчанию.** Старт был на лёгкой MiniLM; eval поиска показал P@5 0.59 против 0.89 у multilingual-e5-large, и агент переведён на e5. Результаты агента v1–v4 получены ещё на MiniLM.
- **Обход для e5-large.** Её веса лежат отдельным файлом, а кэш HuggingFace хранит его ссылкой в общую папку; свежий onnxruntime отказывается читать такие внешние данные. Модель копируется в `models/` без ссылок (папка в `.gitignore`).
- **Модель не ищет сама — она выбирает инструмент.** Товары, цены и составы приходят только из Qdrant, поэтому ассистент не может их выдумать. Задача LLM — понять человека и правильно заполнить аргументы `search_catalog`.
- **Аргументы инструмента нормализуются в коде.** Первая версия держала допустимые значения в enum схемы, но Qwen 7B всё равно прислал `category="крем"` — валидация упала, а модель в ответ выдумала товары. Теперь синонимы приводятся к значениям каталога («крем» → «крем для лица»), неизвестное значение отбрасывается с пометкой для модели, а не с ошибкой.
- **Разговорное → термины каталога делает модель.** «Прыщи» → «акне» описано прямо в docstring инструмента: это дешевле, чем менять модель эмбеддингов, и измеримо на этапе 3.
- **Guardrail-узел `verify` — проверка кодом, а не просьбой в промпте.** На реальном прогоне Qwen 7B: (1) получил пустую выдачу и выдумал три товара с брендами и ценами; (2) ответил на китайском. Промпт «не придумывай» не помог. Узел проверяет, что каждая цена в ответе есть в результатах инструментов этого хода (или это бюджет пользователя), и что в ответе нет иероглифов. Не прошёл — модель получает замечание и пробует снова, после двух неудач уходит безопасная заглушка. Цена выбрана как признак, потому что её нельзя «перефразировать»: выдуманный товар почти всегда приходит с выдуманной ценой.
- **Актив — жёсткий фильтр, и включает его код, а не только модель.** На прогоне «сыворотка с ретинолом» Qwen 7B не передал `active`, получил сыворотки без ретинола и в ответе назвал их «сыворотками с ретинолом». Теперь актив из реплики пользователя распознаётся по основам слов («ретинолом», «салицилка») и фильтр включается автоматически. Первая версия смотрела три последние реплики, и eval поймал, что при смене темы старый актив «прилипает» (A12) — исправлено через границу темы, см. ниже.
- **Условия из реплик извлекает код, модель только дополняет (по результатам eval).** Первый прогон 15 диалогов: Qwen 7B прошёл 53%, 14B — 73%. Главная причина провалов — не галлюцинации (verify не сработал ни разу), а потерянные условия: модель не передавала тип кожи и тип средства из прошлых реплик или, наоборот, сама придумывала категорию, которую пользователь не называл. Теперь тип кожи, тип средства и актив распознаются из реплик пользователя правилами; модель может их дополнить, но не перебить то, что пользователь назвал явно. Текущая «тема» диалога заканчивается на реплике, где назван тип средства, — поэтому «а теперь пенку» сбрасывает ретинол из прошлой темы (кейс A12). Переигровка аргументов модели из первого прогона через новый код: ошибок в фильтрах на 7B было 5 из 9, стало 0.
- **`verify` проверяет и состав.** Каждый актив, названный в ответе, должен быть в составе найденных товаров. Так ловится приписывание товару свойств, о которых спросил пользователь. Если поиск ничего не нашёл, состав не проверяется: совет «попробуйте средства с салициловой кислотой» без товаров — не выдумка (ложное срабатывание нашёл eval, A03).
- **Новое условие — новый поиск.** Если пользователь добавил бюджет, тип кожи или «без отдушек», а агент советует из старой выдачи, `verify` требует повторить поиск. Нашёл eval: 14B на «до 3000» выбрала из прошлой выдачи сыворотку за 3390 ₽.
- **Узел `triage` до LLM.** При признаках заболевания («кровит», «гноится», «быстро растёт») агент не подбирает косметику, а отвечает фиксированным текстом с рекомендацией дерматолога. Модель не участвует: 7B в eval советовала врача и тут же предлагала кремы. Обратный кейс A16 проверяет, что обычные жалобы («стягивает, шелушится») не считаются медицинскими.
- **Пустой `query` не ломает поиск.** На реальном прогоне модель на третьем ходе диалога перестала передавать обязательный `query`: валидация падала, модель видела ошибку и извинялась по кругу. Теперь `query` необязателен, а если он пустой, инструмент берёт последние реплики пользователя из состояния графа (`InjectedState` — модель это поле не видит и не заполняет).
- **Явный граф вместо готового `create_react_agent`.** Тот же цикл ReAct, но видно каждый узел и переход — проще отлаживать и добавлять шаги (например, проверку ответа).
- **`recursion_limit=20`** — защита от бесконечного цикла вызовов инструментов.
- **`temperature=0`** — для подбора важна воспроизводимость, а не креативность; без неё нельзя честно сравнивать версии в eval.
